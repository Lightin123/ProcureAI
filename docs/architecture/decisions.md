# Decisions Log

**Status:** Living document. Records confirmed project decisions and
currently unresolved/open questions. Update this file whenever a new
architectural, product, or process decision is made.

| D26 | Frontend routing uses `react-router-dom` | Milestone 2 introduces multiple URL-addressable screens, and [../design/ui-design.md](../design/ui-design.md) mandates breadcrumbs and a stable page hierarchy |
| D27 | LLM provider is Anthropic; the model is **configured**, not hardcoded (`ANTHROPIC_MODEL`, default `claude-sonnet-5`). Resolves **U6** | Keeps the provider architecture stable while the model can change. Called through the official `anthropic` Python SDK using structured outputs, so responses are schema-validated rather than parsed from free text |
| D28 | AI suggestion traceability uses a single `project_requirements` table with provenance columns (`source`, `status`, `analysis_run_id`, `original_text`, `rejection_reason`). Resolves **U20** for requirements | Bidirectional traceability without the synchronisation burden of separate suggestion and confirmed tables. Applies to requirements only; other data areas decide independently |
| D29 | Requirement taxonomy: `kind` = REQUIREMENT \| CONSTRAINT; `category` = FUNCTIONAL, NON_FUNCTIONAL, BUDGET, TIMELINE, COMPLIANCE, OTHER | `kind` maps to FR2.1 vs FR2.2; the categories cover the constraint examples named in [../product/requirements.md](../product/requirements.md) |
| D30 | Requirement analysis runs **synchronously** with a 60s timeout; no background jobs or queues in Milestone 3. **U16/U17 remain open** | A single analysis call is not the long-running workload the async path in [architecture.md](architecture.md) is reserved for. Revisit if real analyses approach the timeout |
| D31 | Every AI-driven analysis is recorded as a `requirement_analysis_runs` row | Mirrors the Evaluation/Recommendation Runs pattern: re-running never silently overwrites prior output, and failures are recorded rather than lost |
| D32 | `project_stage_history` records every workflow transition from the first one | Milestone 3 introduces the first transitions; retrofitting history later would permanently lose the earliest entries. Serves FR11.1 and NFR4 |
| D33 | Confirmation requires at least one ACCEPTED requirement; unanswered clarifications warn but do not block | The official may reasonably judge open questions unnecessary; a hard block would override their judgement, which conflicts with the human-in-the-loop principle |
| D34 | Explicit reopen is allowed from `REQUIREMENTS_CONFIRMED` back to `REQUIREMENTS_ANALYSIS`. Partially resolves **U22** | Supports the iterative workflow (Workflow Principle 2). Only this pair is defined; other backward transitions stay unresolved |
| D35 | Milestone 3 uses a **fixed AI pipeline**, not an agentic loop | The workflow already makes "Re-run analysis" a human action, so the official is the loop controller. No level-3 agentic component was needed — see [../ai/ai-agents.md](../ai/ai-agents.md) |
| D36 | A deterministic **stub provider** ships alongside the Anthropic provider and is selected automatically when no API key is configured | Keeps the platform runnable and demonstrable without credentials (NFR7), and makes the review workflow testable without incurring API cost |
| D37 | Python tooling is `venv` + `requirements.txt`; the AI service listens on port 8000 and binds to `127.0.0.1` only | No new packaging tooling (no Poetry/uv). Loopback binding enforces the rule that Express is the AI service's only caller |
| D38 | A generic **OpenAI-compatible provider** sits alongside the Anthropic and stub providers, targeted entirely by configuration (`AI_BASE_URL`, `AI_MODEL`) | One implementation covers Groq, xAI/Grok, OpenRouter, Together, and a local Ollama; switching service is a config change, not a code change. Extends D27 rather than replacing it — Anthropic remains available |
| D39 | OpenAI-compatible settings are namespaced `AI_*`, never `OPENAI_*` | Developer machines commonly carry an ambient `OPENAI_API_KEY` for unrelated tools. Using that name caused pydantic-settings to silently adopt the wrong credential during implementation; the namespace prevents it |
| D40 | OpenAI-compatible output uses JSON mode plus Pydantic validation and a bounded retry (`AI_MAX_ATTEMPTS`, default 2) | These endpoints honour JSON schemas less strictly than Anthropic structured outputs. Output that never validates is rejected rather than passed on, satisfying NFR2 |
| D41 | Groq is the project's working LLM provider: `AI_BASE_URL=https://api.groq.com/openai/v1`, `AI_MODEL=openai/gpt-oss-120b`, `AI_MAX_TOKENS=3000` | The only LLM credential available is a Groq free-tier key. The model was chosen from what that key can actually reach — `llama-3.3-70b-versatile` is **not** in Groq's current catalogue. Anthropic and stub providers remain available and unchanged |
| D42 | The provider prompt states the output shape compactly instead of embedding the generated JSON Schema | Groq's free tier caps throughput at 8,000 tokens per minute, and the schema dump consumed roughly a quarter of that per call for no accuracy gain. Cut the system prompt by ~48% |
| D43 | Roadmap re-sequenced: M4 Work Packages, M5 Authentication & RBAC, M6 Vendor Discovery, M7 Evaluation. Authentication moves ahead of vendor work | Vendor representatives need real accounts (see [../product/users-and-roles.md](../product/users-and-roles.md)), so building vendor onboarding before authentication would mean throwaway scaffolding. Work packages depend only on confirmed requirements, so they remain safe to build under the seeded identity (D21). The cost is that M5 must retrofit permission checks across M2–M4 endpoints; this is contained because ownership columns already exist and identity resolves through a single server-side seam |
| D44 | Authentication is **opaque server-side sessions stored in PostgreSQL**, delivered in an `HttpOnly; SameSite=Strict` cookie. Resolves **U3** | Logout must genuinely invalidate a session, which a stateless JWT cannot do without a denylist that reintroduces the database read JWT existed to avoid. Sessions are rows an administrator can inspect, which suits an auditable government system, and they survive an API restart so a demo is not interrupted. `express-session` and external identity providers were rejected — see [../engineering/security.md](../engineering/security.md) |
| D45 | Password hashing uses **`scrypt` from `node:crypto`** (N=16384, r=8, p=1, 32-byte key, 16-byte salt), stored as `scrypt$N$r$p$salt$key` | A memory-hard KDF on OWASP's recommended list, with no native module and therefore no `node-gyp` toolchain requirement — which matters on the Windows development machine and preserves D5's aim of a simple setup. The self-describing encoding lets the parameters be raised later without invalidating existing hashes |
| D46 | **Three roles**, one per user, as the `user_role` enum: `GOVERNMENT_OFFICIAL`, `ADMIN`, `VENDOR`. Government Administrator and Procurement Administrator merge into `ADMIN`; System Administrator is not implemented. Resolves **U4** | The two administrator roles differ only in managing evaluation-criteria templates and compliance checklists, neither of which exists before Milestone 7 — two roles indistinguishable in every implemented surface are one role. System Administrator's entire surface (user management UI, system configuration, audit access) does not exist, so creating it would be scaffolding. Splitting later is a migration on one column |
| D47 | Authorization is **permission-based**: routes declare a permission via `requirePermission(...)`, and `ROLE_PERMISSIONS` in `src/auth/permissions.ts` is the single role-to-permission mapping. Routes never test a role inline | Authorization can be audited by reading one table rather than every route file, and a role change is one edit rather than a search across the codebase |
| D48 | **ADMIN is oversight-only**: read access across its organization, but no `requirements:decide`, `requirements:analyze`, `clarification:answer` or `workflow:transition` permission | A procurement decision must be attributable to the government official who made it (Workflow Principle 6, FR11.1). An oversight role able to confirm another official's requirements would defeat both the audit trail and the accountability model. The accepted cost is that an administrator cannot act for an absent official |
| D49 | Organization scope stays **single organization per user** via `users.organization_id`, and `organizations.kind` (`GOVERNMENT` / `VENDOR`) distinguishes a government department from a vendor company. **Narrows U18 and U19**; bears on **U5** | Nothing in M5–M7 needs multi-organization membership, and the existing scoping already works. `kind` lets vendor users keep the existing `NOT NULL` foreign key instead of weakening it, gives Milestone 6 a clean seam for vendor capability profiles, and makes "this is not a government department" explicit rather than implied by the role |
| D50 | The existing seeded official's `users` row is **promoted in place** by adding a password hash; no new identity and no data migration. Resolves **U28** | The row is already real and already carries a stable UUID that `created_by`, `triggered_by`, `decided_by`, `answered_by` and `actor_id` point at. `ON CONFLICT (email) DO UPDATE` preserves the id, so all existing attribution stays valid and simply becomes true. Verified during implementation: the UUID is unchanged and all eight pre-existing projects remain attributed to it |
| D51 | CSRF is addressed by **`SameSite=Strict`, an `Origin` check on state-changing methods, and the JSON content-type requirement** — no token protocol | The cookie is never attached to a cross-site request, so the attack does not start. Two further independent barriers cover the same class without token plumbing. Must be revisited if the portal is ever served cross-site |
| D52 | `requireAuth` is mounted on the **`/api/v1` prefix**, not per route, so authentication fails closed | A route added by a later milestone is protected whether or not its author remembered. This is the structural mitigation for authentication bypass through an unprotected legacy route, and it is what lets Milestone 4's work-package routes inherit protection at merge with no change |
| D53 | Identity is **request-scoped**: `request.user` is populated by `requireAuth` and read through `getCurrentUser(request)` in `src/auth/currentUser.ts`. `src/repositories/currentOfficial.ts` is deleted | Replaces the seeded resolver of D21. Being a per-request property rather than module state, two concurrent requests cannot observe each other's identity. It also removes a database round-trip per identity read |
| D54 | The public `GET /health` is a **liveness probe only** (`status`, `service`, `timestamp`). Database connectivity, AI-service state, provider, and model move to `GET /api/v1/system/status`, which requires authentication and the `system:status:read` permission | The public endpoint was returning the database state and the name of the third-party LLM provider and model to anyone, so hiding the System Status *page* from vendors would have been cosmetic while the data stayed one unauthenticated request away. A minimal liveness payload also fits D18's stated rationale — standard health-check convention — better than a diagnostics dump. `system:status:read` is granted to Government Officials and Administrators (internal government staff, and officials need to know when the AI service is down) and withheld from Vendors (external parties) |
| D55 | Work-package decomposition (Milestone 4) reuses the requirements provenance pattern from D28: AI-suggested and manually-authored work packages share one table with `source`/`status` columns, plus merge/split/soft-delete lineage in `work_package_history` | Consistency with the reviewed pattern — an official already knows how to accept/edit/reject an AI suggestion from Milestone 3; work packages behave the same way rather than introducing a second mental model |
| D56 | Vendor industry, sub-domain, and solution-type classification is stored as **validated free text**, not a fixed PostgreSQL enum, with the vocabulary defined once in `apps/api/src/vendor/taxonomy.ts` | The vendor taxonomy is expected to grow (new industries, new solution types) as the platform is used by more sectors. A growing enum means a migration per addition; validated text against a server-side vocabulary means the vocabulary is a code change, not a schema change, while still rejecting anything not in the list |
| D57 | Publishing a confirmed project to the vendor portal is a **separate, explicit act** (`published_at`/`published_by`/`opportunity_summary` on `procurement_projects`), distinct from reaching `REQUIREMENTS_CONFIRMED`, and exposes only the official's written summary plus **ACCEPTED** requirements | An official's internal workflow state should not silently determine what becomes visible to external vendors. AI-suggested-but-not-accepted requirements, rationale, and internal notes must never leave the department; a separate publish action with its own summary field is the only way to guarantee that |
| D58 | The vendor onboarding questionnaire is **schema-driven**: one definition in `apps/api/src/vendor/onboardingSchema.ts` (steps, fields, conditional `showIf` rules) is served to the frontend, and the same schema drives client-side rendering, server-side validation, and completion-percentage calculation | A hand-coded form on the frontend and a hand-coded validator on the backend inevitably drift. One served schema means a new question or a new conditional rule is one file, not three, and the two layers cannot disagree about what is being asked |
| D59 | Vendor compliance documents are uploaded as **base64 in the JSON request body** (capped at 8 MB via a path-specific `express.json` limit), stored on local disk under a generated filename, with metadata in `vendor_documents` | Keeps the API to a single content type (JSON) rather than adding multipart/form-data handling for one upload path. The ~33% base64 size overhead is acceptable at an 8 MB ceiling. Storage on local disk, not in PostgreSQL, follows the File/Object Storage design in [architecture.md](architecture.md) |
| D60 | Vendor verification (`vendor-registry` routes) is **not organization-scoped** — an `ADMIN` reviews and verifies suppliers across every vendor organization on the platform, not only their own department's | Verification is a platform-administration duty, not a departmental one; a supplier is not "owned" by any government department. Confined to `ADMIN`, which holds no procurement-decision permission (D48), so the role able to verify a supplier is structurally unable to award them anything — the cross-organization exception does not weaken the accountability model |
| D61 | Vendor self-registration (`POST /api/v1/auth/register`) creates a `VENDOR` account only — the role is a server-side literal, never read from the request body | Prevents a public, unauthenticated endpoint from being used to create a `GOVERNMENT_OFFICIAL` or `ADMIN` account. Government and administrator accounts remain provisioned only by `npm run seed` / a department, consistent with U30 |
| D62 | Vendor-to-opportunity matching is currently **deterministic lexical scoring at project granularity** (`apps/api/src/vendor/matching.ts`); the target architecture is **work-package-granularity hybrid matching** — deterministic eligibility filtering, then lexical + semantic candidate retrieval combined, then multi-factor ranking, with AI used only to narrate evidence, never to decide eligibility or override ranking | A vendor's fit varies per work package within a project, so project-level matching is a coarse proxy, not the target signal — FR4 is specified at work-package granularity. Semantic retrieval is additive to the existing lexical layer, not a replacement, because lexical alone misses vendors who describe a capability differently than the requirement's wording, and semantic alone risks surfacing topically-similar vendors that fail a hard constraint. See [../ai/vendor-discovery.md](../ai/vendor-discovery.md) and [../ai/rag-and-semantic-search.md](../ai/rag-and-semantic-search.md) |

| D63 | **Work-package-level matching is implemented as five separately-testable stages** — normalization, deterministic eligibility, hybrid retrieval, multi-factor ranking, explanation — each in its own module under `apps/api/src/matching/`. Eligibility is a hard gate that runs *before* ranking and is never expressed as a score. Realises the target architecture named in **D62** | Collapsing eligibility into the weighted score would let a strong capability match quietly readmit a supplier who cannot satisfy a mandatory requirement, which is the single most damaging failure this system could have. Keeping retrieval separate from ranking means whichever half found a supplier does not influence where they place. The stage boundaries are also what make the pipeline unit-testable without a database — normalization, eligibility and ranking are pure functions of their inputs |
| D64 | **pgvector is optional at the schema level.** Migration `006` attempts `CREATE EXTENSION vector` inside an exception guard; the vector tables are created only where the extension exists, and `semanticStorageAvailable()` detects their absence at runtime and degrades to lexical-only retrieval. When semantic retrieval is unavailable, its ranking weight is redistributed across the remaining dimensions rather than lost | A migration that hard-fails on `CREATE EXTENSION` would let an unrelated packaging decision on a contributor's machine break authentication, projects and requirements. Vendor discovery is a hybrid of two independent halves and the lexical half needs no extension at all, so the honest failure mode is a degraded ranking with a visible warning, not an unusable feature. Redistributing the weight keeps a lexical-only run on the same 0–100 scale, so two runs remain comparable |
| D65 | **HNSW**, not IVFFlat, for the capability-embedding index, with `vector_cosine_ops`. Resolves the indexing half of **U14** | IVFFlat builds its list structure from the data present at index time and degrades badly on a small or empty table — which is exactly the state the supplier registry starts in and stays in throughout a hackathon demo. HNSW is usable from the first row and needs no rebuild as the registry grows. Cosine matches the normalised vectors the embedding service returns |
| D66 | The **embedding provider is configured independently of the analysis provider**, behind an `EmbeddingProvider` protocol, with three implementations: `local_onnx` (default), `local_concept` (offline fallback) and `openai_compatible` (opt-in via `EMBEDDING_API_KEY`). **Superseded in part by D70** — the default was originally the concept model | Reasoning and retrieval are different capabilities and are not always the same vendor: Anthropic serves the analysis calls and has no embeddings API at all, so tying them together would make the choice of reasoning model decide whether semantic matching works. Hosted embeddings are opt-in on an embedding-specific key rather than on the mere presence of `AI_API_KEY`, because a Groq key set for requirement analysis points at an endpoint with no embeddings route and must not silently start billing per embedding |
| D67 | **Embeddings are regenerated on a source digest, not on a write.** Each stored vector carries a SHA-256 of the exact text embedded plus a pipeline version; a vector is recomputed only when its source text or the pipeline version changes. Sync happens at match time, not on the profile-save path. Resolves **U33** | The capability document is rebuilt on every profile write, but its content usually does not change — embedding on write would mean an API call per keystroke during onboarding, and would put a new external AI dependency on a save path that currently has none (which is what U33 raised against D30's synchronous-analysis constraint). Digest-keyed regeneration at match time gives the same freshness guarantee with no cost for unchanged profiles and no new failure mode on save. A failed regeneration leaves the previous vector in place: a stale embedding retrieves better than none, and deleting it would turn a transient outage into lost data |
| D68 | Every matching run is **persisted with its provenance and its exclusions**: `work_package_match_runs` stores the strategy, normalization, eligibility and ranking versions, the weights used, and the embedding model; `work_package_match_results` stores per-supplier dimension scores, the eligibility result and the supporting evidence — for excluded suppliers as well as recommended ones | A ranking an official acted on must stay interpretable after the weights, the concept lexicon or the embedding model have moved on, and "which suppliers did the system rule out, and on what ground" is a question an official is entitled to ask after the fact. Storing only the recommendations would make the eligibility gate unauditable, which is precisely the part of the pipeline that most needs auditing. Deliberately scoped to this feature rather than built as a general audit framework — FR11's audit log remains a separate concern |
| D69 | **Vendor shortlisting is modelled now, at minimum viable scope** (`work_package_shortlist`: work package, supplier, reason, actor, plus the run and rank/score at the time), with `vendor:shortlist:manage` granted to `GOVERNMENT_OFFICIAL` and withheld from `ADMIN`. Invitation, RFI issue, structured responses and evaluation are **not** modelled. **Invitation built on this seam in Milestone 7** (D73–D76); RFI, structured responses and evaluation remain unmodelled | The matching phase needs somewhere for its output to go, and a shortlist entry is the natural seam. Designing the invitation/response/evaluation tables now — before Milestone 7 specifies that workflow — would produce a schema that is wrong by the time it is used. The rank and score are read server-side from the stored run rather than accepted from the request body, so a shortlist record cannot assert a score the system never produced. Withholding it from ADMIN follows D48/D60: shortlisting is a procurement act and stays with the accountable official |

| D70 | The **default embedding model is `BAAI/bge-small-en-v1.5`**, a real sentence encoder running locally on CPU through `fastembed`'s ONNX runtime — no API key, ~90 MB downloaded once, then offline. The deterministic concept model is retained as the explicit offline fallback (`EMBEDDING_PROVIDER=local_concept`, and automatic if the encoder cannot load). Vector width moves to the encoder's **native 384 dimensions** via migration `007`, not by padding into the existing 1024-wide column. Supersedes the model and dimensionality parts of **D66** | A hand-curated concept lexicon generalises only over the domains somebody wrote down: a sector it does not cover degrades silently towards keyword matching, which is the failure U34 raised. A trained encoder generalises over language it was never told about, which is what semantic retrieval is supposed to buy. Measured on the seeded registry it is also simply better — the intended supplier is top-1 on all four confirmed packages, and the weak-but-plausible match that the concept model scored 40 drops to 28. Padding 384 into 1024 would have preserved cosine exactly and avoided the migration, but it leaves the schema asserting a width no model produces and every future reader having to know that 640 dimensions are structurally zero; the column states the truth instead. Existing vectors are discarded rather than converted — a concept vector has no meaningful projection into encoder space, and the recorded source digest means regeneration is automatic |
| D71 | Embeddings are built from a **semantic document** — the capability-bearing prose alone — not from the full capability document. `vendor_profiles.semantic_document` stores the supplier's; `NormalizedWorkPackage.semanticDocument` is the package's, and excludes its compliance, budget and timeline clauses | A sentence encoder reads a fixed window and averages over it, so every sentence competes for the same vector. Registration numbers, addresses, contact blocks, delivery-model enums and value bands are near identical across suppliers, and compliance and budget clauses are near identical across packages — including them pulls everything towards one point. Measured: embedding the full documents put unrelated package/supplier pairs at 0.75 cosine and ranked a road contractor **above** a farmer producer company for a vegetable supply package; embedding the capability prose alone dropped unrelated pairs to 0.68 and made the intended supplier top-1 in every case. The excluded fields are not lost — they are structured columns the eligibility gate and the ranking dimensions read directly, which is a stronger use of them than blurring them into a vector |
| D72 | Semantic similarity is **calibrated per embedding model** (`apps/api/src/matching/calibration.ts`): each model carries its own retrieval threshold and its own score floor and ceiling, measured against the corpus. An unmeasured model falls back to conservative defaults and the run logs that it did | Cosine is not comparable across models. The encoder places genuinely unrelated procurement text near 0.68 and a strong match near 0.83; the concept model places unrelated text at 0.0. A single threshold cannot serve both — the encoder's numbers fed through the concept model's calibration would admit every supplier as a candidate and score every one of them as a strong match. Keeping the numbers in one table keyed by model means swapping models is a measurement and a row, not a hunt for constants embedded in the ranking code |

| D73 | **Shortlist and invitation actions are audited in `work_package_history`**, the table every other work-package decision already writes to, by extending its action enum with `SHORTLISTED`, `SHORTLIST_REMOVED`, `INVITED`, `INVITATION_WITHDRAWN`, `INVITATION_ACCEPTED` and `INVITATION_DECLINED`. A supplier's acceptance is attributed to the supplier's own user account, not to the department | The question an auditor asks is "what happened to this work package", and a second `work_package_shortlist_history` table would split the answer across two places and oblige every future reader to union them. The existing table already carries actor, action, before/after values, reason and timestamp — exactly the fields a shortlist or invitation decision needs — so the extension is six enum labels rather than a schema. Attributing the response to the supplier's user keeps the row honest: a department must not appear in the record as the author of an acceptance it did not make |
| D74 | **Invitation notifications reuse `vendor_notifications`**, with a new `INVITATION` category and a nullable `invitation_id` foreign key, and are written **in the same request that creates the invitation** | The table already carries registration, submission, verification and document-review events, already has vendor ownership, a link path and a read state, and is already rendered by the portal — an invitation needs none of that built again. Writing the notification inline rather than from a job keeps D30's no-background-work constraint: an invitation that exists is an invitation the supplier can already see, with no window in which the row exists and the notification does not. `invitation_id` is added because "is this notification about a live invitation" is not answerable from a URL string, which is all `link_path` is |
| D75 | An invitation's state machine is `INVITED -> ACCEPTED \| DECLINED \| WITHDRAWN`, enforced by conditional `UPDATE ... WHERE status = 'INVITED'` rather than by a read-then-write, and **there is no `EXPIRED` state**. One live invitation per supplier per work package is enforced by a partial unique index over `status IN ('INVITED','ACCEPTED')` | Making the ownership test and the transition a single statement removes the window in which an invitation could be verified as one supplier's and updated as another's, and makes every transition single-shot without a lock. Expiry would need something to write it, and the only candidate is a background job the system deliberately does not have (D30) — a passed deadline is derived from `response_deadline` at read time, which is the same fact without the machinery. The partial index leaves withdrawn and declined invitations outside the constraint, so re-inviting after either is a fresh, separately audited row rather than a mutation of the one the supplier already answered |
| D76 | The **supplier's view of an invitation is a different query from the department's**, in different repository functions and different routers — not one handler with a role flag. The supplier payload carries no rank, score, dimension breakdown, eligibility verdict, shortlist reason or any other supplier | One handler serving both sides is one `if` away from serving a department's internal assessment to the supplier it assessed, and that failure would be silent. Two queries that never had the columns cannot leak them. The vendor-side functions also take `vendorProfileId` as a non-optional argument applied in the `WHERE` clause, so there is no "find by id" a vendor route could call without it — an invitation id from the browser is never sufficient on its own |
| D77 | A PostgreSQL `date` is converted to its calendar day through `toIsoDay()` (`apps/api/src/repositories/dates.ts`), which reads the parser's local calendar fields, **not** through `toISOString().slice(0, 10)` | `node-postgres` parses `date` into a `Date` at local midnight; projecting that instant back through UTC lands on the previous day for any timezone ahead of UTC. Every user of this system is in IST, so this was not an edge case — it was every date, always one day early. Found while implementing Milestone 7, where an invitation's response deadline is a date a supplier acts on, but the same defect was present on project response deadlines, credential validity and document expiry, so all five call sites now share one helper |
| D78 | **One response configuration per work package, not per supplier.** `work_package_response_configs` holds the response type (`EXPRESSION_OF_INTEREST` / `RFI` / `PROPOSAL` / `QUOTATION`), the deadline, the instructions, a `sections` jsonb map of section id to `OFF` / `OPTIONAL` / `REQUIRED`, and the two switches for clarifications and documents. The response type, the section modes and the document switches become **immutable once any supplier has submitted**; the deadline and the instructions stay editable | A response suppliers are compared on has to be the same response — per-supplier configurations would produce submissions that cannot be laid side by side, which is the reason for collecting them. Freezing the terms after the first submission is the same principle in time rather than across suppliers: adding a mandatory section afterwards would retrospectively make a submitted response incomplete against terms it was never shown, and removing one would discard an answer already given. Extending a deadline disadvantages nobody, so it is not frozen. `sections` is jsonb validated against `responses/schema.ts` rather than a column per section, because adding a section should be a list entry and no query filters on one section's mode |
| D79 | The **section catalogue is one declaration** (`apps/api/src/responses/schema.ts`), served to the frontend and read by the configuration screen, the supplier's form, the progress indicator and the submission check. Section *values* are **explicit columns** on `work_package_responses`, not a jsonb blob | Three readers that must agree about what is being asked for should read one declaration; a second copy in the browser would let a supplier see a progress bar reading 100% for a response the API then refuses, which is the worst version of this failure. The values are columns rather than jsonb for the opposite reason: a quoted value, a proposed start date and a committed team size are facts a department reads and sorts on, and burying them in jsonb would leave every reader re-deriving their types — Milestone 9 among them. Whether a column is required is a property of the configuration, not of the schema, so every one is nullable and the server enforces requiredness at submission |
| D80 | **Completeness is one server-side function** (`responses/completeness.ts`), called both by the read that renders the supplier's progress and by the submit handler that accepts or refuses. Requirement answers, custom questions and mandatory documents are all items in the same checklist | The progress indicator and the submission gate are the same question asked at two moments. Computing them separately — a count in the browser and a check on the server — is how a supplier is told a response is ready and then refused, with no way to find out what is missing. One function also lets the refusal name every missing item, which is what makes it actionable |
| D81 | A response's lifecycle is `DRAFT -> SUBMITTED -> UNDER_REVIEW -> READY_FOR_EVALUATION`, with `UNDER_REVIEW -> CLARIFICATION_REQUESTED -> RESUBMITTED -> UNDER_REVIEW` as the clarification loop and `WITHDRAWN` reachable by the supplier from any state before evaluation. Every transition is a conditional `UPDATE` carrying both the ownership predicate and the permitted source states. **There is no `EXPIRED`**: a passed deadline is derived at read time and enforced at submission against the current calendar day, with a response the department itself asked to have clarified exempt | The same reasoning as D75 applied to a longer machine: putting the ownership test and the state check in one statement removes the window in which a response could be verified as one supplier's and written as another's, and makes every transition single-shot without a lock. Editability is exactly `DRAFT` and `CLARIFICATION_REQUESTED`, which is the whole of "a submitted response cannot be modified" — expressed in the `WHERE` clause of every write rather than in a handler a later route could forget. Expiry would need a background job the system does not have (D30). The clarification exemption exists because refusing a reply the department requested after its own deadline would make its own request unanswerable |
| D82 | **Clarifications are one table for both directions.** `raised_by_side` records which side asked, and it is what decides which side may answer — enforced in the `UPDATE`'s `WHERE` clause, not in a handler. The question is written once and the answer is written once; neither is editable | A clarification is one conversation, and splitting it into a vendor-questions table and a department-requests table would oblige every reader to union them and make "the complete history with actor and timestamps" two queries. Deciding the answerer from the stored side rather than from the caller's role means a department cannot answer its own request and a supplier cannot answer its own question — either would be a record of a conversation that never happened. Immutability is what makes the thread a record rather than a pair of mutable fields |
| D83 | A department **cannot read an unsubmitted draft**. `GET .../responses/:responseId` returns 409 `RESPONSE_NOT_SUBMITTED` while the response is in `DRAFT`; the workspace still shows that a draft exists, whose it is, and that it has not been submitted | Save-as-you-go is what makes a long structured response possible at all, and a supplier that can be read mid-draft has been given a worse tool than a blank page. The department's legitimate interest is "has this supplier started", which the workspace answers, not "what have they written so far". The same rule covers attachments: a document on a draft is not downloadable by the department either |
| D84 | **Response attachments get their own table** (`work_package_response_documents`) but reuse `vendor/documentStorage.ts` for the bytes, which gains an allowlist of upload folders rather than a free-form path | A compliance document belongs to the supplier's profile, is reviewed by a platform administrator and is visible to every department that matches against the supplier; a response attachment belongs to one response, is visible to one department, and is deleted with the response. A shared owner would have been the only reason to share a table, and they do not share one. The bytes still go through the single module that decodes, size-limits and signature-checks an upload, because that is the part it would be dangerous to have two copies of. The folder is an allowlist because a caller that could name an arbitrary directory could name one outside the upload root |
| D85 | Response permissions split three ways: `response:configure` and `response:manage` are `GOVERNMENT_OFFICIAL` only, `response:read` is held by `GOVERNMENT_OFFICIAL` and `ADMIN`, and `vendor:response:read` / `vendor:response:submit` are `VENDOR` only. No role holds a permission from both sides | Configuring what a supplier must submit, and moving a submission through review, are procurement acts and stay with the accountable official (D48, D60, D69). Oversight reads a collected response as it reads a ranking, and acts on neither. Keeping the vendor permissions disjoint from the government ones means the routes that draft, submit and withdraw a response cannot be reached by the side that will read it, and the routes that review it cannot be reached by the side that wrote it — the structural separation D76 established for invitations, applied to the response |

## How to Use This Log

When a decision is made during development (in conversation, in a PR
review, or by explicit instruction), add it to the Confirmed Decisions table
and remove the corresponding row from Open/Unresolved if applicable. Do not
delete resolved decisions — they form the project's history.
